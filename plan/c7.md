# C7 Plan: Homogeneous Options Per-Item Extraction

## Goal

Expose per-item benchmark scores for C7, **Homogeneity of Options**, using the criterion numbering from `human-validation-plan.md`.

C7 asks: are answer options parallel in grammar, length, formatting, and content type?

Current status:
- `HomogeneousOptionsMetric` already exists in `src/metrics/homogeneous_options.py`.
- It internally analyzes and scores each question through fan-out phases.
- It is currently registered as `MetricScope.QUIZ_LEVEL`, so the final `MetricResult` has `question_id=None`.
- Per-question scores are nested in the quiz-level `raw_response` under `question_scores`.
- Roadmap Task 2.3 says C7 needs only an extraction path from `raw_response`.

## Required Behavior

Create a reliable per-item C7 output path without rebuilding the judge.

The final benchmark artifacts must expose C7 scores joinable by `(quiz_id, question_id)`.

Required per-item fields:
- `metric_name`: `"homogeneous_options"`
- `question_id`: the original question ID
- numeric score
- applicability
- severity
- issue labels where available

Do not add duplicate LLM calls just to get per-item C7 scores.

## Implementation Changes

Preferred approach: expand the existing quiz-level metric result into per-question metric results in the runner.

Implementation outline:
- Keep `HomogeneousOptionsMetric.scope == MetricScope.QUIZ_LEVEL`.
- Add an optional hook on metrics, for example `expand_results(...)`, or handle `homogeneous_options` explicitly in `BenchmarkRunner._evaluate_quiz_level`.
- After `metric.evaluate(...)`, parse `result.metadata["phases"]["score_question"]["results"]` or parse `result.raw_response`.
- For each question score result, append a `MetricResult` with:
  - `metric_name="homogeneous_options"`
  - `metric_version=metric.version`
  - `score=question_score`
  - `evaluator_model=evaluator.model_name`
  - `quiz_id=quiz.quiz_id`
  - `question_id=<question_id>`
  - `parameters=parameters`
  - `raw_response` containing the per-question structured score object.
- Preserve the existing quiz-level aggregate only if current reports/tests depend on it. If preserved, avoid double-counting it in validation analysis by documenting that C7 item-level rows have non-null `question_id`.

Alternative approach:
- Convert `HomogeneousOptionsMetric` to `MetricScope.QUESTION_LEVEL`.
- Reuse the existing analyze/score prompt logic for one question at a time.
- Move quiz-level aggregation into reporting.
- Only choose this if it keeps tests simpler and does not break the current aggregate behavior needed elsewhere.

Recommended implementation is the expansion hook because it preserves the working metric and avoids extra calls.

## Tests

Extend existing homogeneity tests:
- A quiz with two applicable questions produces two per-item `homogeneous_options` `MetricResult`s.
- Each expanded result has the correct `question_id`.
- Expanded `raw_response` includes `severity`, `issues`, and `rationale`.
- True/false questions retain the current not-applicable behavior.
- Existing aggregate calculation tests still pass if aggregate output is preserved.

Add runner tests:
- Running a config with `homogeneous_options` produces per-question C7 results.
- If the quiz-level aggregate is also preserved, tests must distinguish aggregate rows (`question_id=None`) from per-item rows (`question_id` non-null).

## Documentation

Update:
- `docs/docs/user-manual/metrics.md`: explain that `homogeneous_options` has quiz-level internals but now exposes per-item results for validation.
- `CRITERIA_COVERAGE_REPORT.md`: keep C7 marked covered, but note the per-item extraction path.
- Any reporting/analysis docs to say C7 validation must use rows with non-null `question_id`.

## Acceptance Criteria

- Validation analysis can obtain C7 without manually parsing nested JSON.
- Every applicable item has a C7 score with `question_id`.
- Not-applicable true/false handling remains explicit and non-crashing.
- No duplicate LLM calls are introduced for C7.
